- Fase 2 (Hardening 1 — DPAPI real) fechado: `WindowsCredentialStore` (em `crates/security/src/windows.rs`) agora fala com a Win32 de verdade via `CredWriteW`/`CredReadW`/`CredDeleteW`/`CredEnumerateW` (crate `windows` v0.58). `TargetName` é `Frederico-IA-Studio:provider:<id>` com persistência `CRED_PERSIST_LOCAL_MACHINE` (criptografia DPAPI por usuário Windows). Mapeamento de HRESULT→win32 corrigido (extrai `& 0xFFFF`) — `ERROR_NOT_FOUND` (1168) é convertido para `Ok(None)` em get e para `Ok(())` em delete (idempotente). `CredFree` é chamado exatamente uma vez por alocação (anteriormente fazia double-free no array retornado por `CredEnumerateW`, causando `STATUS_HEAP_CORRUPTION`). 6 testes de integração em `crates/security/tests/windows_credential_store.rs` (gateados em `#[cfg(windows)]`) com mutex global de serialização e IDs únicos por run: set/get roundtrip, get de inexistente→None, delete idempotente, list filtra prefixo Frederico, list filtra prefixo + valida que credencial semeada de outro app **não vaza**, overwrite de credencial. Casca Tauri (`apps/desktop/src-tauri/src/main.rs`): `AppState.credentials: Arc<WindowsCredentialStore>` único no processo; `ProviderSetCredential`/`ProviderDeleteCredential` agora chamam DPAPI real (não mais `FakeCredentialStore` ad-hoc). `Cargo.toml` de `frederico-security`: `unsafe_code = "deny"` (era `forbid`) para permitir `#![allow(unsafe_code)]` apenas no módulo `windows.rs` e nos tests. `scripts/check-core-purity.ps1` reconhece `crates/security/src/windows*` e `crates/security/tests*` como exceções legítimas. - Fase 2 (Hardening 3 — `provider-recorder`) fechado: novo binário `recorder` em `crates/provider-engine/src/bin/recorder.rs` que faz chamada real a um provedor OpenAI-compat (OpenAI/OpenRouter/DeepSeek/Mistral/NVIDIA NIM/Ollama/LM Studio, configurável via `--base-url`) e grava os bytes brutos do stream SSE num arquivo `.jsonl` com header `# recorded_at=… provider=… model=… base_url=… format=openai-compat-sse`. **Sanitização obrigatória antes do flush**: módulo `frederico_provider_engine::sanitize` (regex case-insensitive bloqueando `Authorization`/`api_key`/`x-api-key`/`Bearer `/`sk-`/`sk-ant-`/`gsk_`/`or-`); o recorder chama `sanitize::check` antes de gravar e, se qualquer token proibido aparecer, **deleta o arquivo** e aborta com exit 1. **Gate de CI**: integration test `tests/fixtures_sanitize.rs` varre `crates/provider-engine/fixtures/**/*.jsonl` no build e quebra o build se algum estiver contaminado ou sem header reconhecido (`# …` do recorder novo ou `{"_fixture_header":…}` legado). - Fase 2 (Hardening 5 — recovery E2E) fechado: **Fase 2 promovida para `concluída`**. 3 integration tests em `crates/provider-engine/tests/recovery.rs` validam a regra do **"Journal de eventos"** (cada `StreamEvent` é persistido em `message_events` **antes** de ser emitido via `EventSink`): `journal_persists_events_across_orchestrator_drop` dispara run com 5 deltas + Done, espera completar, dropa orquestrador A, reabre o mesmo `Database` com orquestrador B, e valida via `MessageEventRepo::list_for_message` que o journal tem o mesmo conteúdo (5 deltas + 1 Done) — provando que o SQLite é a fonte de verdade e sobrevive ao crash do app; `cancel_idempotent_and_status_persists` valida que `cancel_run` é idempotente (pode ser chamado mesmo após o run terminar) e que o status final persistido no db bate com o último status emitido pelo sink; `user_message_persisted_before_run_starts` valida a regra de teste: a `Message.role=user` está no db imediatamente após `send_message` retornar — antes de qualquer I/O de rede. ### Notas
- Fase 0 (Fundação documental) concluída.
- Fase 1 (Fundação desktop) concluída — vertical fino, fim a fim. O usuário agora consegue instalar o `.exe` resultante e abrir o app.
- Fase 2 (Hardening 1 — DPAPI real) fechado. O stub `WindowsCredentialStore` que retornava `Unsupported` foi substituído pela implementação real via Win32; credenciais do usuário agora vão pro Windows Credential Manager criptografadas via DPAPI, não para um shim em memória.
- Fase 2 (Hardening 3 — `provider-recorder`) fechado. O binário `recorder` faz chamadas reais a provedores OpenAI-compat e grava fixtures com header obrigatório; a sanitização regex bloqueia vazamento de credenciais no momento da gravação e o gate de CI quebra o build se um fixture contaminado for commitado.
- Fase 2 (Hardening 4 — contract tests off-PR) fechado. Os 3 tests gateados em env vars (`OPENAI_API_KEY`/`OPENROUTER_API_KEY`/`ANTHROPIC_API_KEY`) pulam limpo sem chave e validam fim-a-fim os adapters contra a API real quando rodam no CI noturno. Runner em `scripts/run-contract-tests.ps1`.
- Fase 2 (Hardening 5 — recovery E2E) fechado. **Fase 2 concluída**. Os 3 tests de recovery validam que o journal de eventos é a fonte de verdade e sobrevive ao drop do orquestrador — equivalente em test ao cenário "app foi morto no meio de um run, reabrir deve mostrar o conteúdo persistido". A regra do "Journal-then-emit" é verificada em três dimensões: persistência do conteúdo (5 deltas + Done), consistência do status final (sink vs db), e ordem das operações (user msg antes do I/O de rede).
- O toolchain de build é Rust stable GNU + MinGW-w64 (não MSVC), por simplicidade no ambiente deste repo. O CI no GitHub Actions usa o toolchain MSVC padrão; ambas as toolchains produzem o mesmo instalador.
- A especificação de origem do produto (PROMPT MESTRE) não é versionada neste repositório; vive como contexto do projeto e é refletida nos arquivos de `docs/architecture/`.
